# Frontend handoff — team and player one-liners

Written for the React frontend's Claude Code session. It describes two backend features that are live on
`env/prod` and have **no frontend yet**: the **team one-liner** and the **player one-liner**. It is the whole
contract — you should not need to read the backend code. Every JSON sample below was captured from a running
backend on 2026-09-13, not typed by hand (two long samples are trimmed where marked).

The product idea, for context: SmallTalkFootball helps someone with no football knowledge hold a casual
football conversation. Until now the app offered one-liners about a *match*. These two features extend the
same idea to a *club* ("what do I say about Manchester City?") and to a *player* ("what do I say about
Haaland?"). Each returns one or two spoken-sounding sentences plus the dry facts behind them so the UI can
render a card.

Suggested opening prompt for the FE session: *"Read `.claude/docs/frontend-handoff-oneliners.md` and plan
the team and player one-liner screens."*

---

## 0. Conventions that apply to every endpoint here

- **All four endpoints are public.** No JWT, no `Authorization` header.
- **Every successful response is the standard envelope** the frontend already knows from `/fixtures`:

  ```json
  { "data": <payload>, "systemMessage": { "messageText": null, "error": false }, "jwt": null, "statusCode": 200 }
  ```

- **Domain errors (404, and the one 400 below) use the same envelope** with `data: null`,
  `systemMessage.error: true` and the message in `systemMessage.messageText`.
- **A missing or invalid query parameter is different**: Spring answers with its own default body
  (`{"status":400,"error":"Bad Request","message":"Required parameter 'lang' is not present.", ...}`), *not*
  the envelope. Treat any non-envelope 400 as a programming error on the FE side — it means a required
  parameter was not sent.
- **`lang` is required on every one-liner call**, one of `BRITISH`, `AMERICAN`, `HEBREW`. This is the language
  the sentence is written in. Hebrew sentences are right-to-left text.
- **Timestamps are ISO-8601 UTC strings** (`"2026-09-20T13:00:00Z"`). Convert to local time for display.
- **Ids are strings**, even when they look numeric (`"80"`, `"659972248"`). Never parse them.
- **The first call for a given (subject, language) is slow — 2 to 5 seconds** — because the sentence is
  generated by an LLM. Repeat calls are instant because the sentence is cached (rules in §3 and §4). The UI
  needs a loading state on the sentence; the facts arrive in the same response, so there is nothing to show
  earlier.
- **`null` in a stat means "not recorded", never zero.** Render it as a dash or omit it. Do not coerce to 0.

Enum values used below:

| Enum | Values |
|---|---|
| `Language` | `BRITISH`, `AMERICAN`, `HEBREW` |
| `Perspective` | `FAN`, `RIVAL_FAN`, `NEUTRAL` |
| `Competition` | `PREMIER_LEAGUE`, `LA_LIGA`, `BUNDESLIGA`, `LIGAT_HA_AL`, `SERIA_A`, `CHAMPIONS_LEAGUE`, `WORLD_CUP` |
| `position` (players) | `"Goalkeepers"`, `"Defenders"`, `"Midfielders"`, `"Forwards"` (strings from the data feed, plural) |

## 1. How the user reaches a team and a player

There is **no team-list endpoint and no player search**. The intended flow is:

1. **Team ids come from fixtures**, which the FE already loads: `GET /fixtures` returns `homeTeam.id` /
   `awayTeam.id` (and name, crest) on every fixture. A team one-liner is one tap away from any fixture, and a
   team page can be reached from either side of a match.
2. **Players come from a team's squad**: `GET /players/teams/{teamId}` (§2) lists the squad in shirt order.
   The user picks one; the app calls the player one-liner with that id.

That is the whole navigation model: fixture → team → player. There is deliberately no free-text search.

## 2. `GET /players/teams/{teamId}` — the squad picker

Returns the stored squad for a team, ordered Goalkeepers → Defenders → Midfielders → Forwards, then by shirt
number. Light shape on purpose: the picker does not need stats, the player card fetches them.

Request: `GET /players/teams/80`

Response (`data` is an array; three of 24 shown):

```json
{
  "data": [
    { "id": "1425703506", "name": "Gianluigi Donnarumma",
      "image": "https://apiv3.apifootball.com/badges/players/52894_g-donnarumma.jpg",
      "number": "1", "position": "Goalkeepers", "injured": false, "matchesPlayed": 9 },
    { "id": "4192878566", "name": "Marcus Bettinelli",
      "image": "https://apiv3.apifootball.com/badges/players/16651_m-bettinelli.jpg",
      "number": "13", "position": "Goalkeepers", "injured": false, "matchesPlayed": null },
    { "id": "3907863339", "name": "Geronimo Rulli",
      "image": "https://apiv3.apifootball.com/badges/players/8352_g-rulli.jpg",
      "number": "28", "position": "Goalkeepers", "injured": false, "matchesPlayed": null }
  ],
  "systemMessage": { "messageText": null, "error": false }, "jwt": null, "statusCode": 200
}
```

Field notes:

- `injured` and `matchesPlayed` are there **only so the picker can grey out or sort** players nobody will
  want to ask about. `matchesPlayed: null` means he has not featured this season (or it is not recorded) —
  a 24-man squad typically has 8–10 of these. Consider showing regulars first or dimming the rest.
- `image` can be `""` for obscure players (seen in Ligat Ha'al). Have a placeholder.
- `number` can be `""`. Blank/non-numeric numbers sort last within their position.
- An unknown or untracked `teamId` returns **`200` with an empty array**, not a 404.
- Squads are refreshed twice a week (Monday and Thursday, 04:00 Israel time). Safe to cache client-side for
  the session.

## 3. `GET /one-liners/teams/{teamId}` — the team one-liner

A sentence about a club, plus its facts.

Query parameters:

| Param | Required | Values | Meaning |
|---|---|---|---|
| `lang` | yes | `Language` | language of the sentence |
| `perspective` | no, default `NEUTRAL` | `Perspective` | who is speaking — see below |
| `competition` | no | `Competition` | which table to talk about; defaults to the club's domestic league |

**Perspective** is the team feature's distinctive control and worth a UI toggle: the same facts phrased as
a supporter of the club (`FAN`: "we're looking sharp"), as a supporter of an unnamed rival (`RIVAL_FAN`:
"they've been lucky"), or with no allegiance (`NEUTRAL`). Each perspective is cached separately, so switching
costs one slow call the first time, then it is instant.

**Competition** matters for clubs in two tables (Champions League clubs). Leave it out for the domestic
league. Passing a competition the club has no standing in silently falls back to the default. Passing
`WORLD_CUP` is ignored.

Field notes:

- `oneLiner.text` is **already one line** (no `\n`), one or two sentences, no emojis. Render as-is.
- `standings` is a map keyed by competition. `primaryCompetition` tells you which key is "the" league table.
  A club can have one or two keys. Show the primary one prominently.
- `recentForm` is most-recent-first, up to 5, and `score` is always written **home-away** regardless of which
  side the club was on — use `home` to read it (`"0-1"` with `home: false` is a 1–0 away win). `result` is
  from the club's point of view: `WIN` / `DRAW` / `LOSS`.
- `nextFixture` is `null` when nothing is scheduled inside the backend's window (about 7 days ahead).
- `notablePlayers` is 0–3 players the sentence may mention (an injured regular, the top scorer, a standout
  keeper). They are **full player records** (same fields as `season` in §4, plus identity); they are handy
  as "ask about a player" shortcuts from the team card — tap one, call §4 with its `id`.
- `venue.*`, `founded`, `coach` can be `""` for smaller clubs.

**Errors**

| HTTP | `systemMessage.messageText` | When |
|---|---|---|
| 404 | `No team was found for id: {id}` | unknown team id |
| 400 | `This team has no league standing, so there is nothing current to say about it.` | a national team, or a club with no table yet — show the message, offer nothing else |

**Caching (what the user will notice):** the sentence is cached per (team, language, perspective,
competition) and regenerated only when the team has played since, or the table moved under it. So the
first request after a match is slow; everything else is instant. Do not add client-side polling — there is
nothing to poll for.

## 4. `GET /one-liners/players/{playerId}` — the player one-liner

A sentence about one footballer, plus his facts and his club's context.

Query parameters: `lang` (required). **No perspective** — a deliberate design decision; there is one voice.

Request: `GET /one-liners/players/659972248?lang=BRITISH`

Field notes, top to bottom:

- **Identity** — `image` may be `""`; `number`, `age` may be `""`. `captain` and `injured` are always booleans.
  An injured player is the single most conversation-worthy thing on a card; show a visible badge.
- **`team`, `competition`, `teamStanding` are `null` together** when the player's club no longer resolves
  (he left the tracked leagues, or the club has no table). The sentence still comes; render the card
  without the club block.
- **`season`** is the flat stat sheet. Every value is nullable and `null` means *not recorded*, not zero
  (Haaland's `interceptions: null` above). `rating` is a string like `"7.30"` or `""`. Goalkeeper-only
  fields (`saves`, `insideBoxSaves`, `goalsConceded`) are `null` for outfield players — hide them unless
  `position === "Goalkeepers"`.
- **`leagueScorerRank`** — his place in the league scoring charts, or `null` when he is not in them. A
  top-5 rank is worth a badge. Note it can be `null` for a genuine top scorer when the data feed holds him
  under two identities; treat `null` as "not shown", never as "not a scorer".
- **`squadContext`** — computed flags that say where he sits in his own squad, which is what turns numbers
  into something worth saying. `appearanceShare` is 0–1, his appearances against the squad's busiest
  player (1.0 = plays everything, 0 = has not featured). `squadSize` is the number of players in the squad.
- **`recentContributions`** — his goals and assists in the club's last five finished matches, most recent
  first, **only the matches where he contributed**. An empty array means none on record, which is the
  normal case for most players and for every defender; show nothing rather than "0 goals". Each entry's
  `fixtureId` links back to the match one-liner the app already has.
- **`nextFixture`** — same shape as the team card; `null` when nothing scheduled. `home` is from the
  player's club's side.

**Errors**

| HTTP | `systemMessage.messageText` | When |
|---|---|---|
| 404 | `No player was found for id: {id}` | unknown player id |

There is no "nothing to say" error for players. A fringe player or one who has not played gets an honest
sentence ("yet to play a minute this season, mind you they're top and unchanged") — every squad member is
askable, which is why the picker in §2 lists all of them.

**Caching:** the sentence is cached per (player, language) and regenerated only when his appearances,
goals/assists, injury flag or scorer rank change, which happens on the twice-weekly squad refresh. So after
the first call, a player's sentence is stable for days. Instant on repeat.

## 5. Behaviour worth designing around

- **Slow first, instant after.** Both one-liner endpoints take 2–5 s the first time for a (subject, language,
  and for teams: perspective + competition). Show the loading state on the sentence area. Do not fire
  requests speculatively for every squad member — each first call is an LLM round-trip.
- **Language switching regenerates.** A new `lang` is a new cache entry and another slow call. If the app has
  a global language setting, expect the first view in a new language to be slow again.
- **Hebrew** sentences are RTL and occasionally transliterate foreign names oddly. Display them in an RTL
  block; do not attempt to fix the names.
- **What the sentence will not do:** it never mentions nationality, transfers, past clubs or anything not in
  `facts`. If a fact looks thin the sentence will be modest rather than inventive. That is intended — the
  card's job is to give the user the supporting numbers.
- **The squad and the stats move twice a week; standings and fixtures move daily.** Client-side caching for
  the session is fine everywhere; there is no need for background refresh.
- **Player images and crests are hot-linked** from `apiv3.apifootball.com`. Plan for a broken image
  fallback.

## 6. Screens this implies (a starting point, not a spec)

1. **Team card** — reachable from either team on any fixture. Crest, name, coach; the sentence with a
   perspective toggle (`FAN` / `NEUTRAL` / `RIVAL_FAN`) and, for two-table clubs, a competition toggle;
   the primary standing (position, points, W-D-L); recent form as five result chips; next fixture; and
   `notablePlayers` as tappable chips leading to the player card.
2. **Squad picker** — from the team card. Grouped by position, shirt numbers, injured badge, dimmed rows for
   `matchesPlayed: null`.
3. **Player card** — photo, name, number, position, age, captain/injured badges; the sentence; club stub
   with standing; the season stat sheet (hide nulls, goalkeeper block only for keepers); scorer-rank badge
   when top-5; recent contributions list linking to match one-liners; next fixture.

All three are read-only and public; no auth state is involved anywhere in this flow.
